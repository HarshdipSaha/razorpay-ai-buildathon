# Product

<!-- impeccable:product-schema 1 -->

**Builder Statement & Human Vision:** As the human builder behind Rebound, my conviction was simple: refuse vanity AI metrics and solve a real, structural friction point in Indian recurring billing. When Razorpay's native retry schedule exhausts on T+3 and subscriptions halt, businesses hemorrhage revenue while merchants are forced into manual chasing. My product vision enforces strict separation of concerns: let AI handle unstructured, messy natural language error descriptions and compose customer nudges, but keep every single money movement, authorization check, and retry bounded by deterministic, audit-logged code. A recovery platform in payments must earn mathematical trust before it earns autonomy.

## Platform

web

## Stack

Python 3.11+ backend (FastAPI, pydantic). The surface in question — the batch report — is a single self-contained HTML string generated by `rebound/sim/report_html.py` from a Python dict; no build tooling, no framework, no external network requests at render time (must render offline, judges may have no internet).

## Users

A Razorpay AI Buildathon judging panel: engineers and product people at a payments company, reviewing a hackathon submission under time pressure, alongside a 5-minute video and a terminal demo. They know payments, fraud, reconciliation, and audit trails professionally — this is not a general consumer audience. Secondarily, the builder themself uses this report during development to check the batch's own correctness.

## Product Purpose

Rebound is an agent that recovers halted Razorpay subscription payments: it classifies why a recurring payment failed (from Razorpay's own documented fields), routes the case through a deterministic policy gate an LLM cannot override, and executes or escalates. The HTML report is the artifact that proves the system worked on a real batch run — the whole "frontend" the judges see, since the actual product is a CLI/backend pipeline with no other UI.

## Positioning

Every number on this report is either a hard invariant (0 double charges, 0 policy violations — must be 0) or traceable to its source (a classification cites the exact Razorpay field it came from; an audit record's hash is inspectable). Competing hackathon reports show a happy-path demo with invented metrics; this one is built to survive a skeptical payments engineer asking "where did that number come from."

## Operating Context

Viewed once per `rebound demo` run, generated fresh each time (not hand-edited), opened locally in a browser with no server. Sits alongside a terminal (pytest, the CLI's own Markdown output) and a video — the report is the "look here for the real numbers" artifact, not the primary interaction surface.

## Capabilities and Constraints

- Must stay a single, self-contained `.html` file written from Python (no separate CSS/JS files, no CDN).
- Must render fully offline — no fonts fetched, no images fetched.
- Data available per render: per-cause allow/block/escalate counts, classifier precision/recall + confusion matrix on a held-out set, an exceptions list, classification-to-source-field citations, a hash-chained audit log (seq/stage/subscription/hash), and an explicit "where AI was/wasn't used" statement.
- Zero login, zero API key — this is a hard product constraint stated elsewhere in the repo (README "Scope decision"), and the report must not imply otherwise.
- No JavaScript interactivity is required (it's a report to read once, not a tool to operate repeatedly) but is not forbidden if it earns its place.

## Brand Commitments

Product name: **Rebound**. Track: Razorpay AI Buildathon, Track 3 (AI Revenue Recovery). No logo, no existing visual identity — the current `report_html.py` output (plain white background, default HTML tables) is not a brand to preserve; it is the incumbent to replace.

## Evidence on Hand

Real batch-run numbers exist and must be used verbatim, never invented: 60 scenarios, 5 duplicates rejected, 0 double charges, 0 policy violations, 100% classifier accuracy / 5% abstain rate on 20 held-out scenarios, 7 causes (insufficient_funds 21, bank_or_gateway_error 12, authentication_failed 9, instrument_expired_or_blocked 6, mandate_not_active 5, unknown 4, limit_exceeded 3), 4 exceptions. Full detail: `docs/hackathon-spec.md`, `FAILURES.md`, `README.md`.

## Product Principles

1. Every claim is either an invariant that must read as zero, or a citation back to a real field/hash — nothing decorative stands in for data.
2. Read once, understood in seconds — a judge has minutes, not the patience to reverse-engineer a dashboard.
3. Technical trust over marketing polish — the aesthetic should read as "built by someone who understands audit systems," not "built to look like a SaaS landing page."
4. Never claim more than the data supports — no invented "₹ recovered," no smoothing over the one abstain case or the 4 escalations.

## Accessibility & Inclusion

**Explicit Builder Preferences:** Full adherence to WCAG 2.1 AA standards across all report and audit interfaces. Crucially:
- Strict tabular numeral styling (`font-variant-numeric: tabular-nums`) so financial amounts and cryptographic hashes align predictably for human inspection.
- Color cannot be the sole conveyor of information: every status indicator (allow, block, escalate) features distinct typography, borders, and explicit text tokens (`CLEAR` / `FLAGGED`) alongside color cues to support colorblind reviewers.
- Full keyboard navigation and visible focus rings on all interactive elements.
- High-contrast text readability (minimum 4.5:1 for normal text, 7:1 for numeric audit tokens against dark backgrounds).
